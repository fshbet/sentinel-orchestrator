# Orchestration research

What was evaluated before the architecture was chosen, what was taken, what was
rejected, and why. This document exists so the decisions in `docs/adr/` can be
argued with rather than merely obeyed.

The brief was explicit that the architecture sketched in the specification is
not automatically optimal. Several parts of it were changed as a result of this
review; those changes are called out under **Departures from the brief** at the
end.

---

## 1. What the system actually has to do

Stripped of vocabulary, the requirement is:

1. Accept an arbitrary objective with no domain hints.
2. Decide what work it implies, and in what order.
3. Find something able to do each piece.
4. Run pieces concurrently where that is safe.
5. Decide, on evidence, whether the objective was met.
6. Survive failure, interruption, and a human saying "wait".

Points 1–3 and 5 need judgement, which means a model. Points 4 and 6 need
determinism, which means software. **The central architectural question is
where the line between them falls**, and most of the differences between the
systems surveyed below reduce to where each one drew it.

---

## 2. Approaches evaluated

### 2.1 Graph-based orchestration (LangGraph and similar)

A workflow is a graph of nodes over a shared state object; edges may be
conditional; the framework drives traversal and persists state at checkpoints.

**Strengths.** The graph is data, so it can be inspected, versioned, and
resumed. Cycles are explicit and bounded rather than emergent. Checkpointing at
node boundaries gives resume almost for free.

**Weaknesses.** The graph is usually authored ahead of time. Generating one per
objective is possible but is not what the model is optimised for, and shared
mutable state across nodes makes concurrency subtle: two nodes writing the same
key is a data race the framework does not see.

**Taken.** The graph as the authoritative plan representation; layered
topological execution; checkpoint-per-node durability.

**Rejected.** A single shared mutable state blob. Task results are passed
explicitly as structured inputs instead, so concurrent tasks cannot silently
collide (`core/domain/models.py`, `TaskResult`).

### 2.2 Orchestrator–worker / planner–executor

A coordinator decomposes and delegates; workers execute in ignorance of the
whole; the coordinator synthesises.

**Strengths.** Maps directly onto capability-based routing. Workers can be
scoped narrowly, which is the security property that matters. Fan-out is
natural.

**Weaknesses.** The coordinator becomes a single point of failure and a context
bottleneck. Naive implementations re-send the whole history to the coordinator
on every step.

**Taken.** The pattern, plus the discipline that a worker's brief is
self-contained (`adapters/execution/base.py`, `AdapterBrief`).

**Rejected.** A coordinator that holds conversational history. The orchestrator
here holds *state*, not a transcript.

### 2.3 Swarm / handoff

Peer agents transfer control to one another; there is no central coordinator.

**Strengths.** Low ceremony, and genuinely good when the next step is obvious to
whoever is currently working.

**Weaknesses.** No global view means no dependency management, no parallelism
worth the name, no reliable termination, and no place to enforce a budget. Loop
detection becomes a heuristic.

**Taken.** Handoff as an *outcome* a task may declare (`TaskResult.handoff_to`),
consumed by the orchestrator.

**Rejected.** Handoff as the top-level control structure.

### 2.4 Evaluator–optimizer

Generate, judge with a separate evaluator, revise.

**Strengths.** The single most reliable quality mechanism available when there
is no deterministic check. Separating the judge from the producer removes the
worst self-assessment bias.

**Weaknesses.** Unbounded in the obvious implementation. Also expensive: each
round is two model calls minimum.

**Taken.** The pattern, with a hard iteration bound and — importantly — each
round materialised as *new tasks* rather than by resetting finished ones, so
terminal states stay terminal and the audit trail shows every round
(`core/execution/engine.py`, `_spawn_optimizer_iteration`).

**Rejected.** Reviving completed tasks in place. It destroys the "terminal is
terminal" invariant that makes the state machine testable.

### 2.5 Durable execution engines (Temporal and similar)

Workflow code is replayed deterministically from an event history; side effects
are recorded as activities.

**Strengths.** The strongest durability story available. Survives process death
mid-step without bespoke recovery code.

**Weaknesses.** Requires a server, imposes determinism constraints on workflow
code, and is heavy for a local single-node run. The determinism requirement sits
awkwardly with a workflow whose *shape* is generated by a model.

**Taken.** Durability by write-ahead of state, and the idea that resumption
should identify completed operations rather than replay them
(`core/state/sqlite_store.py`, `record_operation`).

**Rejected as a requirement.** A workflow-backend interface exists
(`adapters/workflow/base.py`) so a durable engine can be added as a backend, but
nothing needs one to run.

### 2.6 State-machine orchestration

Explicit states, explicit transitions, everything else rejected.

**Strengths.** Invariants become testable. "A failed gate cannot yield
COMPLETED" is a property of the transition table, not a hope about the code.

**Weaknesses.** Rigid on its own. Cannot express a dynamic graph.

**Taken.** Wholesale, for lifecycle. `core/state/machine.py` is the only place a
status changes, and illegal transitions raise.

**Composed with**, not replaced by, the dynamic graph: the state machine governs
the lifecycle, the graph governs the work.

### 2.7 MCP as an integration boundary

A protocol for exposing tools, resources, and prompts to model-driven clients.

**Strengths.** It is the standard worth betting on for tool interoperability.
Capability discovery, structured schemas, and server-declared annotations are
exactly what a capability-routed orchestrator wants.

**Weaknesses.** Server-supplied annotations are self-reported. A server can
describe a destructive tool as read-only, by error or by design.

**Taken.** MCP as a first-class capability boundary, with a native client so the
protocol is not mediated by an SDK's assumptions.

**Rejected.** Trusting annotations. They can only *raise* assessed risk here,
never lower it (`mcp/policy.py`). A tool named `delete_everything` that claims
`readOnlyHint` is still treated as destructive, and the shipped test suite
asserts this.

### 2.8 OpenHands and comparable agent systems

Full agent runtimes with their own loops, sandboxes, and tool sets.

**Strengths.** Mature execution environments. Reimplementing one would be waste.

**Weaknesses.** Their concepts (conversations, events, runtimes) are theirs, not
universal. Adopting them into a core domain model would make the core a client
of one system's worldview.

**Taken.** An adapter (`adapters/execution/openhands.py`), and the general
`SubprocessAdapter` that covers any external worker in any language.

**Rejected.** Any OpenHands concept in the core domain model. There is a test
asserting the core does not reference it.

## 3. Comparison summary

| Approach | Plan is data | Dynamic shape | Parallel | Durable | Bounded loops | Least privilege |
|---|---|---|---|---|---|---|
| Graph-based | yes | partly | yes | yes | yes | no |
| Orchestrator–worker | partly | yes | yes | no | no | yes |
| Swarm / handoff | no | yes | no | no | no | no |
| Evaluator–optimizer | n/a | n/a | n/a | n/a | only if bounded | n/a |
| Durable engines | yes | no | yes | yes | yes | no |
| State machine | yes | no | no | yes | yes | no |
| **This platform** | yes | yes | yes | yes | yes | yes |

No surveyed approach covered the whole requirement, which is why the
architecture composes several rather than adopting one.

## 4. Architectural decisions that follow

1. **Two layers, not one.** A state machine governs the execution lifecycle; a
   dynamic DAG governs the work. Neither can express the other, and trying to
   force one to do both is where the surveyed systems get into trouble.

2. **Patterns are compositional fragments, not modes.** `core/workflow/patterns.py`
   emits task-graph fragments. A parallel fan-out whose merge step is an
   evaluator-optimizer loop is just a graph.

3. **Capability routing over role names.** Roles are the thing that makes a
   framework domain-specific. Capabilities are opaque strings supplied by
   configuration, plugins, or the planner; the core ships none.

4. **The model proposes; software disposes.** State, scheduling, permissions,
   retries, persistence, validation, and limits are deterministic. This is the
   single most consequential decision in the system.

5. **Completion requires evidence.** A validator that cannot check anything says
   so, and the result is `UNCERTAIN`, not `CONFIRMED`. An agent's claim of
   success has no bearing on task status.

6. **Least privilege by construction.** An agent receives the intersection of
   what it declares and what its task needs. It cannot see tools it may not call.

## 5. What was rejected outright

- **A shipped agent library** (`developer`, `tester`, `researcher`, …). Roles are
  configuration. Shipping them would make every user's system look like the
  author's.
- **A shipped workflow library for domains.** Only the generic patterns ship.
- **Markdown-as-implementation.** Markdown is used for agent definitions,
  policies, and docs. The engine is executable software.
- **A single shared mutable state blob** across concurrent nodes.
- **LLM-decided scheduling, retries, and permissions.** Every one of these has a
  correct deterministic answer, and asking a model for it introduces
  nondeterminism with no upside.
- **A mandatory heavyweight durability backend.**
- **Trusting MCP tool annotations.**

## 6. Departures from the brief

The specification's own instruction was to change the design where evidence
warranted. Four places where this implementation differs:

1. **The conceptual diagram implies one linear pipeline** (analyse → discover →
   plan → execute → validate → review). The implementation makes this a
   re-entrant state machine, because iterative planning and recovery both need
   to return to earlier phases. `VALIDATING → PLANNING` is a legal transition;
   in the diagram it is not.

2. **The evaluator-optimizer loop is drawn as a cycle.** Cycles in a task graph
   make cycle detection ambiguous. Here each round appends new tasks, so the
   graph stays acyclic, the bound is explicit, and every round is separately
   auditable.

3. **The brief lists both "IDEMPOTENCY" sections (28 and 67) as separate
   concerns.** They are implemented as one mechanism: an operation log keyed by
   a deterministic id, consulted before any non-idempotent tool call.

4. **"No fake implementation" (section 79) versus test doubles.** A scripted
   model provider exists, because a real model is not deterministic and the
   orchestration logic must be tested deterministically. It is never registered
   automatically, is named for what it is, and the docstring says plainly that
   it is not a production backend.

## 7. Known limitations

Recorded here rather than discovered later.

- **Token estimation is heuristic**, not tokenizer-exact. It deliberately
  over-estimates; a model whose tokenizer is far denser than the assumed ~3.6
  characters per token will under-use its window.
- **Relevance ranking for memory is lexical.** It has no notion of synonymy. The
  interface accepts an embedding-backed scorer; none ships, because that would
  mean a dependency and a model call in the retrieval path.
- **The evaluator-optimizer verdict** is read from an explicit `passed` field in
  structured output. An evaluator that only writes prose is treated as raising
  no objection. This is deliberate — inferring a verdict from prose would be
  guessing — but it means a badly configured evaluator is a no-op.
- **Distributed execution is not implemented.** The `WorkflowBackend` interface
  anticipates it; the shipped backends are single-process.
- **The OpenHands adapter's endpoint paths are configuration** rather than
  pinned constants, because that API changes between releases. The defaults
  match the conversation-oriented API and may need adjusting per deployment.
