# ADR-005: Durability by write-ahead state, with a backend interface for more

**Status:** accepted

## Context

Long-running work must survive pause, resume, retry, cancellation, and process
failure. A durable workflow engine such as Temporal solves this thoroughly, at
the cost of a server, a determinism constraint on workflow code, and a
significant operational footprint.

The determinism constraint is a real tension here: the workflow's *shape* is
generated by a model, which cannot be replayed deterministically.

## Decision

Provide durability directly: every state transition is written before the next is
attempted, `ExecutionEngine.run` is re-entrant, and a side-effect log keyed by a
deterministic operation id stops non-idempotent tool calls being repeated after a
retry.

Define `WorkflowBackend` (`adapters/workflow/base.py`) so a durable engine can be
added later. Ship `LocalWorkflowBackend`, which additionally detects executions a
crash left mid-flight and rewinds only the in-flight tasks - finished work stays
finished.

Require no backend for local use.

## Consequences

**Good.** Nothing to install. Resume works. Interrupted runs do not repeat
completed work.

**Cost.** Durability is at task granularity, not per step inside a task. A crash
mid-tool-call means that call is retried, which is why the idempotency log exists
for non-idempotent tools.

## Alternatives rejected

- **Mandatory durable engine.** Too heavy, and the determinism requirement fits
  badly with model-generated workflows.
- **No durability.** Fails a stated requirement.
